# The agent edits and makes pictures with tools that need no new model, and one optional image service

The agent gets tools for pictures, in four groups. None needs more than the text model with vision (`deepseek-flash` is listed as reading pictures), because the model never has to count pixels or draw pixels:

- **Raster edits** (`edit_picture`): an ordered list of small operations (crop, resize, trim, rotate, flip, a colour made transparent, a circle or rounded mask, grayscale or tint, brightness and contrast, blur, pad, convert) made with sharp, written to a new file. `look_at_picture` shows a picture with a labelled grid so a crop can be given in cells or percentages.
- **SVG** (`svg_outline`, `svg_extract`, `svg_edit`, `write_svg`): parts are chosen by id, copied with the gradients and clip paths they use, and the view box is fitted from bounds measured in Chromium. An SVG the agent writes is rendered and shown back to it.
- **Graphics with text** (`render_graphic`): HTML and CSS rendered to PNG or WebP in the Chromium the editor already has, with the site's fonts and tokens and no network. Share cards, banners, text on a picture.
- **Tracing** (`trace_picture`): potrace, with the bitmap made by sharp. `silhouette` is one colour; `colors` is up to six flat colours traced as layers. The only addition to the Docker image is the `potrace` package.

Raster generation (`generate_image`) exists only when an image service is set up in the Settings drawer, outside the site like the model token (0012). Four kinds of service: OpenAI-style (`/images/generations`, which also serves Together-hosted FLUX), Google (Gemini image by `generateContent`, Imagen by `:predict`), FLUX native from Black Forest Labs (a job, polled, then a signed link) and Runware (one `imageInference` task to `api.runware.ai/v1`, model by its AIR id). Runware also serves the chat model: its chat endpoint is OpenAI-compatible, so it is a provider preset for the agent (`https://api.runware.ai/v1`, models by AIR id such as `deepseek:v4@flash`), and one Runware key can be given to both. Whether a model behind it reads pictures is not documented, so vision stays off for it unless `LLM_VISION=1`. The model name is free text. The tool takes an aspect ratio and, optionally, the width the picture will have on a page; a service that takes pixels gets them (snapped to what it allows), another gets its nearest size tier, and the result says what was made. One picture per call, at most four per reply. A result link is fetched through the checked fetch.

Every SVG that is written or saved is cleaned first (no script, `foreignObject`, event attributes or references to another host, which 0015 already forbids), and stored SVGs are sent with a policy that lets nothing run if one is opened directly. The result of each tool is a new file with its source noted in `pictures.yml`; an original is not overwritten unless asked. A generated picture is flagged `generated: true` with its prompt and service, has no visible label on the site, and the agent says plainly that it is generated.

Rejected: ImageMagick (a large dependency with its own policy file, for nothing sharp cannot do here), the model writing pixel coordinates unaided (it cannot see them), a model-written raster by code (poor results), and a generation service built into the editor (the site must work and the editor must run with only the text model). Cost: a tool that writes an SVG or HTML needs the model to think, so these tools are not in the quiet mode used for content writing (0018); an image service sends the prompt to a third party; a content-security policy by hash (0021) means a graphic's own HTML never reaches the public site, only its image.
